## 一、P0

### #3 播放器无可用暂停、进度条点了没反应

**现象**（报告）：点 ⏸（145,3000）两次时间照走、图标一直是 ⏸；点画面中央只切控制层显隐；点进度条（1000,3050）打开系统最近任务；沿进度条拖动无反应；补偿点按后时间从 0:59 回跳到 0:20。

**根因**（代码层三条，全部实测过）：

1. **中央轻点按设计只切「净屏」**，暂停要靠双击——而 3.0.0 的提示里从没说过，用户根本摸不到。位置见 `onUp()` 的 `mode === "idle"` 分支：首击 `setClean(!clean)`，第二击才 `videoRef.toggle()`。
2. **⏸ 按钮本身是好的**：`onClick → videoRef.toggle() → usePlaybackActivity.pause() → video.pause()` 通路完整，`onPause → setPaused(true)` 也会让图标翻成 ▶（L2 打桩实测见下表）。设备上「点了没反应／时间回跳」是 **#2 点按偏移**把落点挪到了进度条上造成的（0:59 → 0:20 正是一次 seek）。
3. **控制区离屏幕底边太近**：底栏 inset=0 时整块只离底 28px，进度条落在 52–80px 区间，正好压在 Android 手势条上（报告「点进度条打开了最近任务」）。

**改法**：

- `onUp()` 单击改为 **暂停/继续**（180ms 判定窗，双击才净屏，避免双击时先闪一下暂停）；双击仍保留净屏。
- ⏸ 按钮 40 → 44px，补 `onPointerUp` 也 `stopPropagation`，`aria-pressed` 跟播放状态绑定。
- 底部控制块整体上移 16px（`bottomInset + 28` → `+ 44`），进度条底沿从约 52px 抬到约 68px，离开系统手势区。
- 进度条 hitTest 本来就是独立的（`onBarDown/Move/Up` 自己 `stopPropagation` + `setPointerCapture`，不与切集手势共用），未改；拖动/点击都走 `videoRef.seek()`。
- 集数条补「跟随当前集滚动」（切到第 13 集时当前 chip 常在视口外，看起来像没选中）。

**状态** ⚠（L2 已验通路，真机待复测）

| 验的什么 | 怎么验 | 结果 |
|---|---|---|
| ⏸ 是否真调 `video.pause()` | 打桩 `HTMLMediaElement.pause/play` + `paused` getter，真 touch 点按钮 | `pause()` 被调用、`paused` 变 true |
| 图标是否跟播放状态双向同步 | 派发真实 `pause` 事件 | `aria-label` 从「暂停」→「播放」 |
| 再点一次是否恢复播放 | 同一次会话 | `play()` 被调用、回到播放态 |
| 中央轻点是否暂停 | `Input.dispatchTouchEvent` 点画面中央 | `pause()` 被调用，**控制层没有消失** |
| 按钮/进度条位置 | DOM | 按钮 y 638–682（屏高 792），进度条 696–724，底沿距屏底 68px |

### #7 轮播：滑动/点圆点/自动轮换全无效

**现象**：hero 固定「神瞳觉醒 第一季」，横滑两次不动、点第 2 个圆点不动、3 分钟无自动轮换。

**根因**（三条独立的）：

1. **圆点热区只有 3px 高**（`.hg-spotlight-bar { height:3px; width:18px }`）。视觉上就是 3×18 的细条，手指按 3px 高的东西基本按不中——按不中自然「点了没反应」。这是「圆点成了纯装饰」的直接原因。
2. **自动轮换的定时器在重构时整个丢了**：3.0.0 的 `Home.tsx` 里没有任何 `setInterval`，圆点只是索引指示器。
3. 横滑手势 W18 已补（本轮保留、未改）。

**改法**：

- 圆点视觉不变，用 `::after` 把热区上下各扩 12px（3px → 27px 可点高度）。L2 实测：圆点上下 ±10px、右侧 +12px 的点按都命中按钮本身。
- 恢复自动轮换：6s 一页，只在「推荐」分栏可见 + 页面在前台时走；手动切页（圆点/横滑）会把定时器重置，不会刚点完就被换走。
- 确认 `setHeroIndex` **真的驱动 hero 切换**（不是只改高亮）：`hero = heroes[safeHeroIdx]` 是数据驱动的，L2 点第 3 个圆点后标题从「网调我的冰山妈妈」变为「少妇白洁」，`data-on` 同步。
- W18 的 `heroTouch` 手势原样保留，L2 回归：左滑 130px → 索引 0→1、hero 换片。

**状态** ✅

## 二、P0（报告最严重的系统性问题）

### #2 点按落点与响应不一致（越靠下偏得越多，约 140px）

**结论：代码层没有找到坐标换算错误，不建议在本轮改代码。**

代码审计（逐项过）：

| 查什么 | 结果 |
|---|---|
| `index.html` viewport | `width=device-width, initial-scale=1.0, viewport-fit=cover`，没有 `maximum-scale` / 固定宽度 |
| `tauri.conf.json` windows | 1200×780 是桌面窗口配置，Android 由生成的工程全屏，不影响手机 |
| `html/body/#root` 高度 | `height:100%; height:100dvh; overflow:hidden`，无 JS 钉死高度（`main.tsx` 里已注释掉旧做法） |
| 有没有把 `screen.height` / `innerHeight` 用于命中换算 | **没有**。只有两处：`isLandscape` 判定（`innerWidth > innerHeight`）和诊断日志 |
| 有没有 `transform: scale()` 缩放整页 | 没有。只有视频舞台的 `zoom`，且限制在视频容器内 |
| 手势 handler 是否自己换算坐标 | 没有，全部用 `clientX/clientY` 直接与 DOM 比对 |

偏移量与报告吻合：`140 / 3168 ≈ 4.4%`，正是「内容视口 1440×3028 被拉伸到 1440×3168」这种**覆盖面分辨率下 WebView 视口 ≠ 触摸空间**的比例错位，属系统/容器层，不是应用层。

**改法（只加诊断，不动坐标）**：`src/layoutDiagnostics.ts` 原来只在 iOS 采集，现在安卓也采。装上后 `debug.log` / 播放诊断里会同时打出 `screen`（物理）、`window.innerHeight`（CSS）、`visualViewport`、`100vh` / `100dvh` 探针实测值、`#root` 实际矩形 —— 真机上这四组数一对，就能确定是覆盖分辨率还是应用换算。

**状态** ⚠ **需小米9 真机（不设 `wm size`）复核**

- 若小米9 上落点准确 → 结论是 phone2k 覆盖分辨率所致，报告里要写明「模拟器覆盖分辨率的触摸映射问题，非应用 bug」。
- 若小米9 上也偏 → 拿上面四组数回来再定位（那时才动代码）。

### #5 字幕压住时间读数（字幕烧在画面里）

**现象**：片源自带的大号白字字幕盖住左下 `0:26 / 4:58`，时间看不全。

**根因**：字幕是**烧进视频画面**的，不是独立字幕轨——所谓「字幕层与控制栏分层」在客户端做不到（没有可控制的那一层）。3.0.0 只在控件层加了一条 168px 的渐变，但读数本身是裸字，字幕正压上去就糊。

**改法**（报告给的第二个方案「时间/进度条加半透明底衬」）：

- 新 `.hg-video-time`：`rgba(0,0,0,.46)` 底 + 6px 背景模糊 + 1px 内描边 + 12px/600 白字，把「当前 / 总时长」做成底衬胶囊。
- 底部渐变压暗从 `.6` 提到 `.72`、高度 168 → 196，覆盖到集数条下沿。

**状态** ⚠（L2 量到 `.hg-video-time` 92.3×26、底衬生效；字幕实际叠压只能在真机看片时确认）

### #12 详情页 点赞/收藏/评论 三组数字被右缘切掉

**现象**：「点赞 18.5 万 · 收藏 10.9 万 · 评论」——「评论」只剩半截字，评论数完全看不见。

**根因**：这一行塞在 `.hg-detail-head` 里，而 head 只有 **166px 宽**（宽幅区 304 = 海报 126 + 间距 12 + head 166）。三组数字在 11–12px 下需要 ~194px，`nowrap + overflow-x:auto` 只会把它从右缘硬切掉，横向滚动又没有视觉提示。

**改法（跨海报通栏，定稿）**：把计数行从 head 里移到宽幅区底部，`left/right:14px` **通栏 304px**，head 上抬到 `bottom:36px`：

- 字号 **12px**（不缩小）、`·` 分隔、组间距 8px、`flex-wrap: nowrap`；
- 三组「标签+数字」各自 `nowrap`，永不拆开；
- 实测：整行 **1 行**、右缘 251.5px（宽幅区右缘 346px，余量 94px）、`scrollWidth - clientWidth = 0`（无溢出）、行高 18px、与海报底间距 6px。
- 元信息行顺带改成「两组不可再拆的单元」（`9.8 分 · 更新至 12 集` / `共 12 集`），放得下就一行，放不下只在两组之间换行——既不会把「共」留在行尾，也不会像单行省略那样把「共 N 集」整段藏掉（166px 装不下 178px，实测为 2 行，两行都是完整语义）。

**状态** ✅（L2 实测单行、无裁切、无溢出；截图复核人物比例与排版正常）

## 七、画面比例自查（用户要求：画面比例正常）

方法：逐类容器取 `getBoundingClientRect()` 的比例，与该容器内 `<img>` 的 `naturalWidth/naturalHeight` 比，再乘 `object-fit` 判「裁」还是「拉」。

| 容器 | 容器比 | 图片原始比 | object-fit | 裁掉 | 结论 |
|---|---|---|---|---|---|
| 详情页海报 `.hg-detail-poster` | 0.750 | 0.750 | **contain** | 0% | ✅ 原图完整不裁 |
| 详情页宽幅底图 `.hg-detail-hero-bg` | 1.185 | 0.750 | cover | — | 装饰用（模糊+压暗），不读内容 |
| 3 列网格海报 `.hg-poster-art` | 0.750 | 0.750 | cover | **0%** | ✅ |
| 热播风向标 `.hg-top10-art` | 0.753 | 0.750 | cover | **0.4%**（原 138% 时 2.7%） | ✅ 已改 133.3333% |
| 首页主推 hero `.hg-spotlight` | 1.557 | 0.750 | cover | 51.8% | ⚠ 设计是 16:10 影院横幅（报告 UI 1-4 要求 358×220≈16:10），裁上下是版式本身，非拉伸 |
| 独家原创宽画幅 `.hg-wide-art` | 1.724 | 0.750 | cover | 56.5% | ⚠ 同上，是「宽画幅剧照」版式（`padding-top:58%` 有注释） |
| 策展专题小卡 `.hg-topic-mini-art` | 1.923 | 0.750 | cover | 61% | ⚠ 同上，专题卡是 2:1 通栏卡 |

**结论**：

1. **没有一处拉伸变形** —— 全站图片/视频只用 `object-fit: cover | contain`，没有任何 `fill` / 固定宽高拉伸；视频 `VideoSurface` 按 `fit` 在 `object-cover`（竖屏源铺满）和 `object-contain`（横屏源保黑边）之间切，两种源都不会被拉。
2. 海报类容器里，**3:4 的占 4 类且全部零裁切**（网格、详情、榜单小封面色块）；唯一的偏差是热播风向标 138% → 已对齐到 133.3333%。
3. 三处 51–61% 的裁切是**版式选择**（16:10 影院横幅 / 宽画幅剧照 / 2:1 专题卡），不是 bug：这类卡片对 3:4 竖版封面必然裁上下。要零裁切只能改成「模糊封面铺底 + 原比例封面居中」（详情页首屏就是这套），属于改版式——按「不发明设计」本轮没动，需要的话单独开一条。

**视频两种源的实际行为**（代码层）：竖屏 9:16 源在 360×792 屏上 `cover` → 左右各裁约 9.6%（画面不拉长、不压扁）；横屏 16:9 源在竖屏下走 `contain` → 上下黑边、不裁不拉；进全屏（`fs`）后横屏源仍 `contain`。

### #17 点「全屏」不横屏（**已改为：恢复入口 + 伪横屏 + 修好旋转后的控件与命中**）

**背景更正**：上一轮按报告建议把这个按钮删了，用户回退意见是「以前都能横屏，现在反而不行」——对用户来说删除就是功能退化。**入口已恢复。**

**事实核查**：所谓「横屏」在非 iOS 平台从来不是系统方向 API —— `set_orientation` 在 `#[cfg(not(target_os = "ios"))]` 分支是空实现；真正让画面横过来的是前端把整块舞台 `rotate(90deg)`（`.fs-landscape`）+ 尝试 `screen.orientation.lock`。

**改法**：

1. **入口恢复**：竖屏控制行重新有「⛶ 全屏」（`aria-label="全屏横屏播放"`），走 `enterFs(true)`：锁住当前屏 → `fs=true` + `fsLandscape=true` → 先试 `documentElement.requestFullscreen()` + `screen.orientation.lock('landscape')`（真横屏），拿不到就用 `.fs-landscape` 的 CSS 旋转做成**伪横屏**（用户把手机横过来看）。
2. **旋转后控件不再消失**：伪横屏下全屏控制条（暂停 / 时间 / 铺满·适应 / 倍速 / 下集 / 总时长 + 进度条 + 右上「退出全屏」）都在 canvas 内按 canvas 坐标系排布，实测都在安全区内。
3. **命中跟旋转走**：恢复 `stageXY(rotated, x, y)`（`src/mobileHold.ts`），把屏幕坐标换算回舞台坐标后再做长按分区 / 横拖定位 / 上下划切集 / 双击判定；进度条本来就按 `rotated` 用 Y 轴取百分比，保持不变。
4. **再点一次回竖屏**：右上「退出全屏」→ `setFs(false)+setFsLandscape(false)` + 解除方向锁/全屏 + 重新显示控件。
5. **铺满 / 适应**：伪横屏下多一个切换键（`portraitFit`），默认「适应」不裁，想要铺满自己切（铺满会裁边）。

**伪横屏的物理限制（写清楚，避免下次又当 bug 报）**：不转系统方向时，9:16 的剧集放进 16:9 的横屏舞台只能二选一——留黑边（默认，不裁内容）或裁掉约 75% 才能铺满。所以默认给「适应」，铺满作为可选。

**真系统横屏的工作量与风险（本轮不做）**：需要在 `src-tauri` 加 Android JNI/Kotlin 实现（`Activity.setRequestedOrientation` + 恢复时还原），并且要处理 `configChanges` 引发的 WebView 重建、播放中断、全屏层与系统栏的配合；本地无法编译验证（容器无 NDK），必须走 CI 出包 + 真机迭代，估计 1–2 轮构建（每轮约 20 分钟）才稳定。**结论：能做，但不是一次性小改，建议单独排期。**

**状态** ⚠ L2 已验（`fs-landscape` 生效、控件齐全、点暂停命中、退出回竖屏），真机手感待验

## 八、播放页控件显隐 & 选集入口（本轮新增，回应「一进界面就显示集数」「控件不自动出现」）

**现象**：3.0.0 一进播放器，底部就摆着一整行集数 chips；上一轮把中央轻点改成「暂停/继续」后，用户又反馈「控件不自动出现 / 要乱点才出来」。

**根因**：

1. 集数条是常驻渲染的（`!fs && !clean` 就直接挂 12 个 chip），挤压标题与进度区。
2. `clean` 是 store 里的状态，可能残留上一轮的 `true`；一旦为真，所有 `!clean` 门禁的控件都不出现——表现为「进播放器什么都没有」。
3. 上一轮的单击语义里没有「控件已收起 → 轻点唤回」这一态。

**改法（三态语义 + 自动隐藏）**：

| 状态 | 画面 | 轻点 | 双击 |
|---|---|---|---|
| 控件显示（默认） | 视频 + 顶部返回/标题 + 播放键 + 进度区 + 一行操作（选集/详情/设置/全屏） | **暂停 / 继续** | 沉浸净屏（收起控件） |
| 控件收起 | 只有画面 | **唤回控件（不暂停）** | — |
| 全屏层 | 舞台 + 全屏控制条 | 唤回 / 暂停 | 收起控制条 |

- **进播放器 / 切集强制显示控件**（`setClean(false)`）+ 重启计时，残留状态不再影响首屏；
- **自动隐藏**：显示后 **4.5s** 无操作收起；**暂停中、面板打开时不收**；任何手势/按钮操作都会重新计时；
- **集数条默认不摆**：换成行内「选集 · 第 N 集 / 共 M 集」按钮，点了弹底部面板（`EpisodesPanel`），面板打开时**当前集自动滚到中间高亮**（36 集的剧也能一眼看到自己播到哪）；
- 面板跟随控件：面板是 Sheet，控件收起时它本来就不可见；关面板/点外部即收起。

**状态** ⚠ L2 五条路径全过（见下），真机待验

| 路径 | 预期 | 实测 |
